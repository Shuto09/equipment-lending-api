# SQL の実行計画（EXPLAIN の実測）

- この文書は Claude Code（Anthropic の AI）で作成しました。
- 目的: [要件と設計 §10](要件と設計.md#10-mybatis-の動的-sql-とページング) の「索引が効く所・効かない所」を、架空のデータで実際に確かめる。
- 実測日: 2026-10-04。数値はこの 1 回の実測で、性能の目標や保証ではありません。

## 条件

| 項目 | 値 |
|---|---|
| DB | `postgres:17` の公式イメージ（PostgreSQL 17.11）。設定は既定のまま |
| マシン | Docker の動く Linux マシン（Intel Core i5-6400・4 コア・メモリ 15 GB） |
| データ | 利用者 1,000 人・備品 5,000 台（うち廃棄済み 500）・返却済みの貸出 50,000 件・未返却の貸出 1,500 件（うち 2026-10-04 時点の延滞 727 件）。すべて架空。作り方は [explain/data.sql](explain/data.sql) |
| SQL | アプリが実際に発行した文（MyBatis の DEBUG ログの `Preparing` の文）の `?` を、同じログの `Parameters` の値に置き換えたもの（[explain/queries.sql](explain/queries.sql)）。各文は 1 回空読みしてから `EXPLAIN (ANALYZE, BUFFERS)` を取った |

実行したコマンド（`compose.yaml` と同じ `postgres:17` のコンテナの中に空の DB `explain_check` を作り、V1 と架空データを流してから、問い合わせを流す）:

```sh
docker exec -i <postgres のコンテナ> createdb -U lending explain_check
cat src/main/resources/db/migration/V1__create_tables.sql docs/explain/data.sql   | docker exec -i <postgres のコンテナ> psql -U lending -d explain_check -v ON_ERROR_STOP=1 -q
cat docs/explain/queries.sql   | docker exec -i <postgres のコンテナ> psql -U lending -d explain_check -v ON_ERROR_STOP=1
```

## 結果の要約

| # | 文 | 読み方 | 実行時間 |
|---|---|---|---|
| Q1 | 備品検索の一覧（`keyword=pc`・`availability=AVAILABLE`・`sort=name,desc`・20 件） | 備品は順次走査（`'%pc%'` の `ILIKE` は B-tree 索引を使えない）。未返却の貸出は部分一意インデックス `uq_loans_open_equipment` から 1,500 行だけを読んでハッシュ結合。貸出状態の `CASE` の絞り込みは結合の後 | 6.719 ms |
| Q2 | 備品検索の件数（同じ条件） | Q1 と同じ走査と結合をし、条件に合う行をすべて数える（`LIMIT` が無いので途中で止まらない） | 6.279 ms |
| Q3 | 延滞一覧（20 件） | 部分索引 `ix_loans_open_due_date (due_date, id)` を並び順のまま読み、20 行で止まる（並べ替えの処理が無い） | 0.178 ms |
| Q4 | 延滞一覧の件数 | 未返却の行（1,500 行）を `uq_loans_open_equipment` から読み、期限で絞る | 0.305 ms |

- 設計の見込み（§10）どおり、備品検索は索引がほぼ効かず、延滞一覧は部分索引の順に読めた。
- Q1・Q2 では、貸出状態の `CASE` 式で絞り込んだ後の行数の見積もりが 16 行、実際は 300 行で、見積もりが外れている（式の結果の分布は統計に無く、既定の見積もりになるため）。データが増えて結合の方法の選び方に響くようなら見直す。
- 備品が増えて Q1・Q2 が遅くなったら、キーワードは `pg_trgm` の GIN 索引、ページングはキーセット方式に切り替える（§10）。この実測では、そこまでの必要は確かめていない。
