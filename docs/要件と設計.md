## 1. 目的と読み手

- 目的: 社内の備品（ノート PC・モニター・プロジェクターなど）の登録・検索・貸出・返却・延滞の確認を行う REST API。
- このリポジトリは**サンプル**です。業務ロジックの設計、SQL（MyBatis の動的 SQL）、トランザクションと排他制御、テストの組み立てを、短時間で読める量に収めることを優先します。機能の多さは目標にしません。
- 想定する読み手: Java / Spring Boot のコードを読むエンジニア。

## 2. 範囲と範囲外

| 範囲（作る） | 範囲外（作らない） |
|---|---|
| 備品の登録・検索・詳細・更新・廃棄 | ログイン・認証基盤（§12 のデモ方式で代用） |
| 貸出・返却・貸出一覧・延滞一覧 | 利用者の登録・編集 API（初期データで用意） |
| 入力検証とエラー応答（ProblemDetail） | 予約・期限の延長申請・承認フロー |
| OpenAPI（Swagger UI）による API 定義の公開 | 通知（メール・チャット）・画面（UI） |
| DB のマイグレーション（Flyway） | 数量管理（1 備品＝1 台。「モニター 10 台」は 10 件で登録） |
| 自動テスト一式と CI | 監査ログ・物理削除・CSV 入出力・本番環境へのデプロイ |

## 3. 用語とユースケース

| 用語 | 意味 |
|---|---|
| 備品 | 管理番号（例 `PC-0001`）を持つ 1 台の物。区分はノート PC・モニター・プロジェクター・その他 |
| 貸出 | 1 人の利用者が 1 台の備品を借りている記録。返却するまで「未返却」 |
| 返却期限 | 貸出時に決める日付（日単位・日本時間） |
| 延滞 | 未返却のまま返却期限の翌日以降になった状態。保存せず、毎回「今日」と比べて求める |
| 廃棄 | 使わなくなった備品の扱い。取り消さない。廃棄済みは貸せない |
| 利用者の役割 | `MEMBER`（一般）と `ADMIN`（備品の管理者） |

| # | 誰が | 何をする |
|---|---|---|
| UC-1 | ADMIN | 備品を登録する・名称や区分を直す・廃棄する |
| UC-2 | 全員 | 備品をキーワード・区分・貸出状態で探す |
| UC-3 | 全員 | 空いている備品を返却期限を決めて借りる |
| UC-4 | 借りた本人か ADMIN | 返却する |
| UC-5 | 全員 | 貸出の一覧を見る（MEMBER は自分の分だけ） |
| UC-6 | ADMIN | 延滞の一覧を、延滞日数の多い順に見る |

### 受け入れ条件（テスト名の元になる文）

| ID | 前提（Given） | 操作（When） | 結果（Then） |
|---|---|---|---|
| AC-01 | ADMIN | 正しい入力で備品を登録 | 201・`Location` ヘッダ・貸出状態は `AVAILABLE` |
| AC-02 | 同じ管理番号が登録済み | 登録 | 409 `ASSET_CODE_DUPLICATED` |
| AC-03 | MEMBER | 登録・更新・廃棄・延滞一覧 | 403 `FORBIDDEN` |
| AC-04 | 備品が複数 | キーワード・区分（複数）・貸出状態で検索 | 条件に合う物だけが、指定の並び順とページで返る。`%` `_` は文字として扱う |
| AC-05 | — | 許可していない並び替えキーで検索 | 400 `VALIDATION_FAILED`（SQL は実行しない） |
| AC-06 | 空いている備品 | 今日〜14 日後の期限で借りる | 201・その備品は `LENT` |
| AC-07 | 貸出中の備品 | 借りる | 409 `EQUIPMENT_ALREADY_LENT` |
| AC-08 | 廃棄済みの備品 | 借りる | 409 `EQUIPMENT_DISPOSED` |
| AC-09 | 延滞中の貸出がある利用者 | 別の備品を借りる | 422 `BORROWER_HAS_OVERDUE` |
| AC-10 | 未返却が 3 件の利用者 | 4 件目を借りる | 422 `LOAN_LIMIT_EXCEEDED` |
| AC-11 | — | 期限を昨日・15 日後で借りる | 422 `DUE_DATE_OUT_OF_RANGE`（今日と 14 日後は通る） |
| AC-12 | 未返却の貸出 | 本人か ADMIN が返却 | 200・`returnedAt` が入る。期限後の返却は `returnedLate=true`。他の MEMBER は 403、返却済みは 409 `LOAN_ALREADY_RETURNED` |
| AC-13 | 期限切れ・期限内・返却済みが混在 | 延滞一覧 | 期限切れの未返却だけが、延滞日数の多い順に返る |
| AC-14 | 貸出中の備品 | 廃棄 | 409 `EQUIPMENT_IN_USE`。空いていれば廃棄でき、以後は貸せず、検索の既定の結果から消える |
| AC-15 | 備品を 2 人が同じ `version` で読んだ | 2 人目が更新 | 409 `VERSION_CONFLICT`（1 人目の変更を上書きしない） |
| AC-16 | 空いている備品 1 台 | 別々の利用者が同時に借りる | 成功は 1 件だけ。残りは 409 `EQUIPMENT_ALREADY_LENT`。未返却の貸出は 1 件 |
| AC-17 | 未返却 0 件の利用者 | 別々の備品を同時に 6 件借りる | 成功はちょうど 3 件。残りは 422 `LOAN_LIMIT_EXCEEDED`。未返却の貸出は 3 件 |
| AC-18 | 空いている備品 | 廃棄と貸出が同時 | 「廃棄済みなのに未返却の貸出がある」状態が生まれない |
| AC-19 | `X-User-Id` なし・数字でない・存在しない利用者 | 任意の API（利用者を使わない検索・詳細、本文が不正な要求も含む） | 401 `UNAUTHENTICATED`（400 より先） |
| AC-20 | 想定外の例外 | 任意の API | 500 `INTERNAL_ERROR` と `traceId`。SQL やスタックトレースを応答に含めない |
| AC-21 | MEMBER と ADMIN | 貸出一覧 | MEMBER は自分の分だけ（`borrowerId` を省くと自分に固定、他人を指定すると 403）。ADMIN は全員分 |
| AC-22 | 他人の貸出 | MEMBER が詳細を見る | 403 `FORBIDDEN`（本人と ADMIN は 200） |
| AC-23 | ADMIN・最新の `version` | 名称・区分・備考を更新 | 200・送った項目だけが変わり `version` が 1 増える。変更する項目が 0 個・空白だけの名称は 400 |
| AC-24 | 貸出中の備品 | MEMBER が検索・詳細を見る | 借り手の表示名と返却期限が出る。メールアドレスは出ない（§6） |

## 4. 業務ルール

| # | ルール | 守る場所 |
|---|---|---|
| R1 | 1 台の備品に未返却の貸出は同時に 1 件まで（二重貸出の禁止） | **DB 制約**（部分一意インデックス）＋サービスの判定 |
| R2 | 廃棄済みの備品は貸さない・更新しない | 貸出: 備品行をロックした後に判定／更新: 条件付き UPDATE（`status = 'ACTIVE'`） |
| R3 | 貸出中の備品は廃棄できない | サービス（備品行をロックした後に判定） |
| R4 | 返却期限は「今日」から「今日＋14 日」まで（両端を含む） | サービス（今日は `Clock` から） |
| R5 | 延滞中の貸出が 1 件でもある利用者は新しく借りられない | サービス |
| R6 | 1 人の未返却は 3 件まで | サービス（利用者行をロックした後に数える。理由は §8） |
| R7 | 返却できるのは借りた本人か ADMIN。返却は 1 回だけ | サービス＋条件付き UPDATE |
| R8 | 備品の登録・更新・廃棄、延滞一覧は ADMIN だけ | サービス |
| R9 | 延滞は「未返却かつ返却期限 < 今日」。保存しない | SQL（今日はアプリから渡す） |

- 数値（14 日・3 件）は `application.properties` の `lending.max-loan-days`・`lending.max-open-loans-per-borrower` で変えられる。業務日付のタイムゾーンは `lending.zone=Asia/Tokyo`。
- 判定の順番（複数に当たる時にどのエラーを返すか）。認証（401）と入力の形式（400）は §12 のとおりサービスより前に済んでいる。サービスでは安い判定から順に行い、ロックを取る前に入力だけで分かる物を弾く。

| 操作 | 判定の順番 |
|---|---|
| 貸出 | ① 期限の範囲（R4・422）→ ② 利用者行をロック → ③ 備品行をロック。無ければ 404 → ④ 廃棄済み（R2・409）→ ⑤ 貸出中（R1・409）→ ⑥ 延滞あり（R5・422）→ ⑦ 件数上限（R6・422）→ 登録 |
| 返却 | ① 貸出が無い（404）→ ② 本人か ADMIN でない（403）→ ③ 条件付き UPDATE が 0 件＝返却済み（409） |
| 廃棄 | ① ADMIN でない（403）→ ② 備品行をロック。無ければ 404 → ③ 廃棄済み（409）→ ④ 貸出中（R3・409）→ 更新 |
| 更新 | ① ADMIN でない（403）→ ② `version` を条件にした UPDATE（楽観ロック）。0 件なら読み直して 404／409 `EQUIPMENT_DISPOSED`／409 `VERSION_CONFLICT` を判定 |

### 状態遷移

保存するのは備品の `status`（`ACTIVE` / `DISPOSED`）と貸出の `returned_at` だけ。API が返す貸出状態（availability）はそこから求める。

```mermaid
stateDiagram-v2
    [*] --> AVAILABLE: 登録
    AVAILABLE --> LENT: 貸出
    LENT --> AVAILABLE: 返却
    LENT --> OVERDUE: 返却期限を過ぎる（日付が変わるだけ・書き込みなし）
    OVERDUE --> AVAILABLE: 返却
    AVAILABLE --> DISPOSED: 廃棄
    DISPOSED --> [*]
```

`LENT`・`OVERDUE` から `DISPOSED` へは行けない（R3）。いったん返却してから廃棄する。

| availability | 条件 |
|---|---|
| `DISPOSED` | `equipment.status = 'DISPOSED'` |
| `AVAILABLE` | `ACTIVE` で、未返却の貸出が無い |
| `LENT` | `ACTIVE` で、未返却の貸出があり、返却期限 ≥ 今日 |
| `OVERDUE` | `ACTIVE` で、未返却の貸出があり、返却期限 < 今日 |

## 5. データモデル

```mermaid
erDiagram
    users ||--o{ loans : "借りる"
    equipment ||--o{ loans : "貸し出される"
    users {
        bigint id PK
        varchar display_name
        varchar email UK
        varchar role "MEMBER / ADMIN"
    }
    equipment {
        bigint id PK
        varchar asset_code UK "管理番号"
        varchar name
        varchar category "LAPTOP / MONITOR / PROJECTOR / OTHER"
        varchar remarks "備考・任意"
        varchar status "ACTIVE / DISPOSED"
        timestamptz disposed_at
        integer version "楽観ロック"
        timestamptz created_at
    }
    loans {
        bigint id PK
        bigint equipment_id FK
        bigint borrower_id FK
        timestamptz lent_at
        date due_date "返却期限（日本時間の日付）"
        timestamptz returned_at "NULL＝未返却"

```

テーブルは 3 つ（＋ Flyway の管理表）。DDL は `src/main/resources/db/migration/V1__create_tables.sql` に置く。方針は次のとおり。

```sql
CREATE TABLE equipment (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    asset_code  varchar(20)  NOT NULL,
    name        varchar(100) NOT NULL,
    category    varchar(20)  NOT NULL,
    remarks     varchar(500),
    status      varchar(10)  NOT NULL DEFAULT 'ACTIVE',
    disposed_at timestamptz,
    version     integer      NOT NULL DEFAULT 0,
    created_at  timestamptz  NOT NULL,
    CONSTRAINT uq_equipment_asset_code UNIQUE (asset_code),
    CONSTRAINT ck_equipment_category CHECK (category IN ('LAPTOP', 'MONITOR', 'PROJECTOR', 'OTHER')),
    CONSTRAINT ck_equipment_status   CHECK (status IN ('ACTIVE', 'DISPOSED')),
    CONSTRAINT ck_equipment_disposed CHECK ((status = 'DISPOSED') = (disposed_at IS NOT NULL)),
    CONSTRAINT ck_equipment_remarks_not_empty CHECK (remarks <> '')
);

CREATE TABLE loans (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    equipment_id bigint      NOT NULL REFERENCES equipment (id),
    borrower_id  bigint      NOT NULL REFERENCES users (id),
    lent_at      timestamptz NOT NULL,
    due_date     date        NOT NULL,
    returned_at  timestamptz,
    CONSTRAINT ck_loans_returned_after_lent CHECK (returned_at IS NULL OR returned_at >= lent_at)
);

-- 二重貸出の禁止（R1）: 未返却の行だけを対象にした一意インデックス
CREATE UNIQUE INDEX uq_loans_open_equipment ON loans (equipment_id) WHERE returned_at IS NULL;
-- 延滞一覧（R9）: 未返却の行だけを、一覧の並び順（期限・id）と同じ順で持つ
CREATE INDEX ix_loans_open_due_date ON loans (due_date, id) WHERE returned_at IS NULL;
-- 外部キー側の索引（PostgreSQL は自動では作らない）
CREATE INDEX ix_loans_equipment ON loans (equipment_id);
CREATE INDEX ix_loans_borrower  ON loans (borrower_id);
```

`users` は `id`・`display_name`・`email`（一意 `uq_users_email`）・`role`（CHECK `ck_users_role` で 2 値）だけの小さな表。制約名は Java の定数（`DbConstraints`）と一致させ、一意制約違反を「どの制約か」で分けるのに使う（§9）。

### 制約で守るもの・アプリで守るもの

| 守るもの | 場所 | 理由 |
|---|---|---|
| 二重貸出の禁止（R1） | 部分一意インデックス | どの経路（別のアプリ・手作業の SQL・将来のバグ）から書いても破れない。正しさの最後の砦 |
| 管理番号・メールの一意 | 一意制約 | 同上 |
| 区分・状態・役割の値 | CHECK | 値の追加は DDL 1 行で済み、MyBatis の enum の名前保存とそのまま合う（PostgreSQL の ENUM 型は使わない） |
| 廃棄済みと廃棄日時の整合・返却日時 ≥ 貸出日時・備考の空文字なし | CHECK | 1 行の中で閉じる規則なので DB に置ける |
| 廃棄済みは貸さない・貸出中は廃棄しない（R2・R3） | アプリ（行ロックの後で判定） | 2 つの表にまたがる。トリガで書くと規則が Java から見えず、単体テストもしにくい |
| 期限の範囲・延滞者・件数上限（R4〜R6） | アプリ | 「今日」に依存する、または集計が要る。CHECK では書けない |
| 権限（R7・R8） | アプリ | 利用者の役割は要求ごとに変わる文脈 |

- 時刻はアプリの `Clock` から渡す。**1 操作で `Clock` を読むのは最初の 1 回だけ**（`Instant now`）。今日の日付は `now` を `lending.zone` で変換して求め、判定と保存の両方に同じ値を使う（日本時間の 0:00 をまたいでも、期限の判定に使った日付と `lent_at`・`returned_at` の日付が食い違わない）。
- **SQL の中で `now()`・`CURRENT_DATE` などの時刻関数を使わない**（時刻を決める場所を 1 か所にし、テストで固定できるようにする）。テスト計画 §3 で機械的に検査する。
- `timestamptz` は Java の `OffsetDateTime` で受ける（JVM の既定タイムゾーンに結果を左右させない）。応答の日時は DB から読んだオフセットに頼らず `lending.zone`（日本時間）に揃える。
- ID は `bigint` の IDENTITY。物理削除はしない。

## 6. API 一覧

共通: `/api/**` のすべての API に `X-User-Id` ヘッダが要る（認証の位置と順番は §12）。成功時は `application/json`、失敗時は `application/problem+json`。日付は `yyyy-MM-dd`、日時は ISO 8601（オフセット付き）。

| # | メソッド | パス | 権限 | 入力 | 成功 | 主なエラー |
|---|---|---|---|---|---|---|
| 1 | POST | `/api/equipment` | ADMIN | 本文: `assetCode`・`name`・`category`・`remarks`? | 201・`Location`・備品 | 400・403・409 `ASSET_CODE_DUPLICATED` |
| 2 | GET | `/api/equipment` | 全員 | `keyword`?・`category`（複数可）・`availability`?・`sort`?・`page`?・`size`? | 200・備品の一覧（ページ） | 400 |
| 3 | GET | `/api/equipment/{id}` | 全員 | — | 200・備品（貸出中なら借り手の表示名と返却期限を含む） | 404 `EQUIPMENT_NOT_FOUND` |
| 4 | PATCH | `/api/equipment/{id}` | ADMIN | 本文: `name`?・`category`?・`remarks`?・`version`（必須） | 200・備品（`version` が 1 増える） | 400・403・404・409 `EQUIPMENT_DISPOSED`・409 `VERSION_CONFLICT` |
| 5 | POST | `/api/equipment/{id}/dispose` | ADMIN | — | 200・備品（`DISPOSED`） | 403・404・409 `EQUIPMENT_DISPOSED`・409 `EQUIPMENT_IN_USE` |
| 6 | POST | `/api/loans` | 全員（借りる本人） | 本文: `equipmentId`・`dueDate` | 201・`Location`・貸出 | 400・404・409 `EQUIPMENT_ALREADY_LENT`・409 `EQUIPMENT_DISPOSED`・422（3 種） |
| 7 | GET | `/api/loans` | 全員（MEMBER は自分の分だけ） | `state`?（`OPEN`/`RETURNED`/`ALL`・既定 `OPEN`）・`borrowerId`?・`equipmentId`?・`sort`?・`page`?・`size`? | 200・貸出の一覧（ページ） | 400・403（MEMBER が他人の `borrowerId` を指定） |
| 8 | GET | `/api/loans/{id}` | 本人か ADMIN | — | 200・貸出 | 403・404 `LOAN_NOT_FOUND` |
| 9 | POST | `/api/loans/{id}/return` | 本人か ADMIN | — | 200・貸出（`returnedAt`・`returnedLate`） | 403・404・409 `LOAN_ALREADY_RETURNED` |
| 10 | GET | `/api/loans/overdue` | ADMIN | `page`?・`size`? | 200・延滞の一覧（延滞日数の多い順） | 403 |

- 入力の検証（Bean Validation）: `assetCode` は `^[A-Z]{2,4}-[0-9]{4}$`、`name` は 1〜100 字で空白だけは不可（`@Pattern(regexp = ".*\\S.*")`）、`remarks` は 500 字まで、`keyword` は 50 字まで、`page` は 0〜10000、`size` は 1〜100（既定 20）。クエリパラメータは `@RequestParam` で 1 つずつ受け、制約は引数に直接付ける。
- `page` に上限を置くのは、`page × size` が int の範囲を超えて OFFSET が負になり、PostgreSQL のエラー（500）になるのを防ぐため。`PageQuery#offset` も long で計算する。
- PATCH は **JSON Merge Patch（RFC 7396）ではない独自の部分更新**で、`Content-Type` は `application/json`。送らない項目と `null` は「変えない」。備考を消す時は空文字を送り、保存の前に `NULL` にそろえる（DB の「空」は `NULL` の 1 種類だけ）。変更する項目が 1 つも無い要求は 400（`version` だけが上がる更新を作らない）。
- 貸出の応答の `state` は `LENT` / `OVERDUE` / `RETURNED`。`returnedLate` は返却日（日本時間）が期限より後なら `true`。
- 見せる範囲の方針:
  - **今の持ち主は全員に見せる。** 貸出中の備品の借り手（表示名）と返却期限は、検索・詳細で全員に返す（社内の台帳。借りたい人が今の持ち主に直接頼めるように）。延滞していることも検索（`availability=OVERDUE`）で分かり、隠す情報としては扱わない。
  - **貸出の履歴は本人と ADMIN だけ。** 誰が過去に何を借りたか（貸出一覧・貸出詳細）は他の MEMBER に見せない。他人の貸出の詳細・返却は 403 にする（404 で存在を隠さない。貸出の ID の存在は社内で隠す情報ではなく、403 の方が利用者が原因を取り違えない）。
  - **メールアドレスは延滞一覧（ADMIN）にだけ出す。** 延滞一覧を ADMIN に限るのは、連絡先を並べることと、催促が管理者の仕事であるため。他の応答は表示名まで。

応答の例（貸出の成功・201）:

```json
{
  "id": 42,
  "equipment": { "id": 7, "assetCode": "PC-0007", "name": "ノート PC 14 インチ" },
  "borrower": { "id": 3, "displayName": "山田 太郎" },
  "lentAt": "2026-10-05T10:15:00+09:00",
  "dueDate": "2026-10-12",
  "returnedAt": null,
  "state": "LENT",
  "returnedLate": false

```

ページの形: `{ "items": [...], "page": 0, "size": 20, "totalElements": 42, "totalPages": 3 }`

## 7. エラーの表し方（ProblemDetail・RFC 9457）

- `@RestControllerAdvice`（`ResponseEntityExceptionHandler` を継承）1 か所で `ProblemDetail` を組み立てる。Spring MVC 自身が投げる例外も、`handleExceptionInternal` を 1 か所で上書きして `code`（入力系は `errors` も）を付ける。**すべての失敗応答に `code` が付く。**
- `type`: 業務エラーと入力検証は、コードごとの URI（`https://example.com/problems/` ＋ code を小文字・ハイフンにした値）。`example.com` は RFC 9457 自身の例に合わせた仮の値で、実運用では自分のドメインにして説明ページを置く（§16 Q3）。HTTP の状態以上の意味が無いもの（存在しないパスの 404・405・406・415・500）は `about:blank`。
- `title`: コードごとの固定の文（例「貸出中の備品です」）。`about:blank` のものは HTTP の状態の名前（例 `Not Found`）。`detail` はその要求に即した日本語の説明。
- `code`（拡張メンバー）: 機械で判別する値。`ErrorCode` の enum が「code ↔ HTTP 状態 ↔ type ↔ title」の対応表の正本。業務エラーは `BusinessException(ErrorCode, detail)` で投げる。
- `errors`（入力検証だけ）: 項目ごとの理由の配列。本文の項目は `{"pointer": "#/assetCode", "detail": "…"}`（JSON Pointer）、クエリパラメータは `{"parameter": "size", "detail": "…"}`。
- `traceId`（500 だけ）: 要求ごとに作る ID。同じ値をスタックトレースと一緒にログへ出し、問い合わせとログを突き合わせられるようにする。

```json
{
  "type": "https://example.com/problems/equipment-already-lent",
  "title": "貸出中の備品です",
  "status": 409,
  "detail": "備品 PC-0007 は貸出中です",
  "instance": "/api/loans",
  "code": "EQUIPMENT_ALREADY_LENT"
}
```

| code | 状態 | いつ |
|---|---|---|
| `VALIDATION_FAILED` | 400 | 形式・桁・必須の違反、許可していない並び替えキー、JSON や日付の形が読めない（`errors` に項目） |
| `UNAUTHENTICATED` | 401 | `X-User-Id` が無い・数字でない・存在しない |
| `FORBIDDEN` | 403 | 役割や本人の条件を満たさない |
| `EQUIPMENT_NOT_FOUND` / `LOAN_NOT_FOUND` | 404 | 対象が無い |
| `ASSET_CODE_DUPLICATED` | 409 | 管理番号の重複 |
| `EQUIPMENT_ALREADY_LENT` | 409 | 貸出中の備品を借りようとした |
| `EQUIPMENT_DISPOSED` | 409 | 廃棄済みの備品を借りる・更新する・もう一度廃棄する |
| `EQUIPMENT_IN_USE` | 409 | 貸出中の備品を廃棄しようとした |
| `LOAN_ALREADY_RETURNED` | 409 | 返却済みの貸出を返却しようとした |
| `VERSION_CONFLICT` | 409 | 更新の `version` が古い |
| `DUE_DATE_OUT_OF_RANGE` | 422 | 返却期限が今日〜14 日後の外 |
| `BORROWER_HAS_OVERDUE` | 422 | 延滞中の利用者が借りようとした |
| `LOAN_LIMIT_EXCEEDED` | 422 | 未返却が上限に達している |
| `NOT_FOUND` / `METHOD_NOT_ALLOWED` / `NOT_ACCEPTABLE` / `UNSUPPORTED_MEDIA_TYPE` | 404 / 405 / 406 / 415 | 存在しないパス・許可していないメソッド・JSON 以外の応答を求めた・本文が JSON でない |
| `REQUEST_REJECTED` | その他の 4xx | 下の表のどれにも当たらない Spring MVC の例外（この API の経路では起きない想定） |
| `INTERNAL_ERROR` | 500 | 想定外。応答には一般的な文と `traceId` だけを返し、詳細はログに出す |

Spring MVC の例外と code の対応（`handleExceptionInternal` で付ける）:

| Spring MVC の例外 | 起きる時 | 状態・code | `errors` |
|---|---|---|---|
| `MethodArgumentNotValidException` | `@Valid @RequestBody` の制約違反 | 400 `VALIDATION_FAILED` | `pointer` |
| `HandlerMethodValidationException` | `@RequestParam` に付けた制約（`@Max` など）の違反 | 同上 | `parameter` |
| `MethodArgumentTypeMismatchException` | クエリの型変換の失敗（`category=FOO`・`page=abc`） | 同上 | `parameter` |
| `MissingServletRequestParameterException` | 必須のクエリパラメータが無い（今は必須のものは無い） | 同上 | `parameter` |
| `HttpMessageNotReadableException` | 壊れた JSON・読めない日付や区分 | 同上 | 項目が分かれば `pointer`（Jackson の例外が持つ位置から） |
| `NoResourceFoundException` | 存在しないパス | 404 `NOT_FOUND` | — |
| `HttpRequestMethodNotSupportedException` | 許可していないメソッド | 405 `METHOD_NOT_ALLOWED` | — |
| `HttpMediaTypeNotAcceptableException` | JSON 以外の応答を求めた | 406 `NOT_ACCEPTABLE` | — |
| `HttpMediaTypeNotSupportedException` | 本文が JSON でない | 415 `UNSUPPORTED_MEDIA_TYPE` | — |
| 上記以外で `ResponseEntityExceptionHandler` が扱うもの | — | 状態はそのまま。4xx は `REQUEST_REJECTED`、5xx は `INTERNAL_ERROR` | — |

- `@Valid @RequestBody` の違反は、同じメソッドの他の引数に制約が付いていると `MethodArgumentNotValidException` ではなく `HandlerMethodValidationException` で届く（Spring 6.1 以降のメソッド検証）。どちらで届いても同じ形にする。
- 状態の使い分け: **400** は要求の形式の誤り。**409** は操作対象のリソース（備品・貸出）の今の状態と衝突した（貸出中・廃棄済み・返却済み・`version` が古い・管理番号の重複）。**422**（RFC 9110 での名前は Unprocessable Content）は、形式は正しいが業務規則に反する（期限の範囲・申請者の延滞・件数の上限）。他の人の操作が原因かどうかでは分けない（件数の上限は同時の貸出でも起きる＝テスト計画 CT-3）。

## 8. 排他制御（二重貸出をどう防ぐか）

結論: **二重貸出の禁止は DB 制約（部分一意インデックス）で保証する。** 2 つの表にまたがる判定（廃棄と貸出・件数上限）は、悲観ロック（`SELECT … FOR UPDATE`）で同じ備品・同じ利用者への操作を直列化する。楽観ロック（`version` 列）は「人が画面で直す備品情報の上書き防止」にだけ使う。

| 守るもの | 手段 | なぜその手段か |
|---|---|---|
| 1 台に未返却 1 件（R1） | 部分一意インデックス `uq_loans_open_equipment` | 貸出は「行の追加」なので、`version` 列（楽観ロック）では守れない。楽観ロックで守るには貸出のたびに備品行も更新する必要があり、無関係な備品情報の編集まで 409 になる。制約ならアプリの判定を飛ばした経路でも破れない |
| 廃棄と貸出の競合（R2・R3） | 備品行の悲観ロック | 貸出は「備品が廃棄済みでない」ことを、廃棄は「未返却が無い」ことを、それぞれ相手の表で確かめる（書き込み先が違う＝write skew）。同じ備品行のロックを両方が取れば必ず直列化される |
| 1 人 3 件まで（R6） | 利用者行の悲観ロック | 同じ人が別々の備品を同時に借りると、数えた時点ではどちらも 2 件で通ってしまう。件数そのものはロックできない（集約関数には `FOR UPDATE` を付けられず、これから入る貸出の行はまだ無い＝ファントム）。そこで、その人の貸出全体を代表する利用者行をロックして直列化する |
| 備品情報の更新（AC-15） | 楽観ロック（`version` 列） | 人が画面を見てから保存するまでの時間はロックを持てない長さ。後から保存した人の変更で前の人の変更を黙って消さないよう、409 で知らせる |
| 返却の二重実行（R7） | 条件付き UPDATE（`WHERE returned_at IS NULL`）の更新件数 | 1 文で判定と書き込みが終わる。0 件なら返却済み |

- 分離レベルは PostgreSQL の既定の READ COMMITTED のまま。ロックを取った**後の文**は新しいスナップショットで読むので、相手の確定した結果が見える。
- **ロックの順番は「利用者 → 備品」で固定**（貸出だけが両方を取り、廃棄は備品だけ、返却は取らない）。順番が逆になる組み合わせが無いのでデッドロックは起きない。
- 二重の守り: 通常はロックの後の判定で `EQUIPMENT_ALREADY_LENT` を返す。判定をすり抜けて INSERT が一意制約に当たった場合も、**制約名が `uq_loans_open_equipment` の時だけ** `DuplicateKeyException` を `EQUIPMENT_ALREADY_LENT` に変換する（500 にしない）。他の制約なら変換せず 500 にして、原因を取り違えない。PostgreSQL は制約違反の後の文を受け付けないので、変換したらそのまま例外を投げてロールバックする。
- ロックは 1 台・1 人の単位で、トランザクションは数文で終わる。待ちが長くなる場面は想定していない（数値の目標は置かない。測っていないため）。

二つの貸出がぶつかった時の流れ:

```mermaid
sequenceDiagram
    participant A as 貸出 A（山田さん）
    participant DB as PostgreSQL
    participant B as 貸出 B（佐藤さん）
    A->>DB: users id=1 FOR UPDATE
    B->>DB: users id=2 FOR UPDATE
    A->>DB: equipment id=7 FOR UPDATE（取れる）
    B->>DB: equipment id=7 FOR UPDATE（A の終了まで待つ）
    A->>DB: 未返却なし → INSERT loans → COMMIT
    DB-->>B: ロック取得
    B->>DB: 未返却を確認 → 1 件ある
    B-->>B: 409 EQUIPMENT_ALREADY_LENT（ROLLBACK）
```

## 9. トランザクションの境界

- `@Transactional` は**サービスの公開メソッドだけ**に付ける。コントローラとマッパーには付けない。
- 一覧（備品検索・貸出一覧・延滞一覧）は `@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)`。件数（`COUNT(*)`）と中身（`SELECT`）は別の 2 文なので、READ COMMITTED だと間に確定した貸出や廃棄で `totalElements` と `items` が食い違う（例: `availability=AVAILABLE` で件数は 5 なのに中身は 4 件）。REPEATABLE READ なら 2 文が同じスナップショットを読む。PostgreSQL では読み取りだけのトランザクションは REPEATABLE READ でも直列化エラーにならないので、再試行は要らない。
- 詳細（1 文）は `readOnly = true` だけ（READ COMMITTED）。
- 業務エラーは実行時例外（`BusinessException`）なので、投げればロールバックされる。
- 一意制約違反は制約名で分ける。`uq_equipment_asset_code` → `ASSET_CODE_DUPLICATED`、`uq_loans_open_equipment` → `EQUIPMENT_ALREADY_LENT`、それ以外は変換しない（500）。制約名は `PSQLException#getServerErrorMessage().getConstraint()` から `DbConstraints` 1 か所で取り出す。
- 時刻は 1 操作 1 回だけ `Clock` から読む（§5）。

| 操作 | ロック | 書き込み |
|---|---|---|
| 登録 | なし（一意制約違反を制約名で 409 に変換） | `INSERT equipment` |
| 更新 | 楽観ロック（`WHERE id = ? AND version = ? AND status = 'ACTIVE'`） | `UPDATE equipment`（`version + 1`） |
| 廃棄 | 備品行の悲観ロック | `UPDATE equipment`（`DISPOSED`・`disposed_at`・`version + 1`） |
| 貸出 | 利用者行 → 備品行の悲観ロック | `INSERT loans` |
| 返却 | なし（条件付き UPDATE） | `UPDATE loans SET returned_at` |
| 一覧 | なし（readOnly・REPEATABLE READ） | — |
| 詳細 | なし（readOnly） | — |

## 10. MyBatis の動的 SQL とページング

- マッパーはインターフェース（`@Mapper`）＋ XML（`src/main/resources/mapper/**/*.xml`）。SQL はすべて XML に書き、注釈（`@Select`・`@SelectProvider` など）は使わない（テスト計画 §3 で Java 側も検査）。
- 値はすべて `#{}`（バインド変数）で渡す。**マッパー XML に `${}` を 1 つも書かない**（テスト計画 §3 で機械的に検査）。
- 並び替えは**許可リスト方式**: 要求の `sort=name,desc` を Java の enum（例 `EquipmentSortKey`）に変換し、知らないキー・向きは 400 にする。XML では enum の名前を `<choose>` で列に対応させるので、利用者の入力が SQL の文字列に入る経路が無い。並びが同じ行はいつも `id` で並べ、ページの境目で行が重複・欠落しないようにする。
- キーワードは名前と管理番号の部分一致（大文字小文字を区別しない `ILIKE`）。`%`・`_`・`\` は Java 側でエスケープしてから渡す（`100%` で「100」から始まる全件が当たらないように）。
- ページングは `LIMIT #{size} OFFSET #{offset}` と件数の `COUNT(*)` の 2 文（同じスナップショットで読む。§9）。絞り込みの `WHERE` は `<sql>` 断片にして両方から `<include>` する（条件の食い違いを防ぐ）。
- 貸出状態（availability）は内側の SELECT で 1 回だけ `CASE` で求め、外側で絞り込み・並び替えに使う（判定式を 1 か所にする）。
- 未返却の貸出を `LEFT JOIN` しても備品の行は増えない（部分一意インデックスで未返却は 1 台 1 件まで）。制約が SQL の正しさの前提にもなっている。

備品検索の骨格（実装の目安。列の一部を省略）:

```xml
<sql id="equipmentWithAvailability">
  SELECT e.id, e.asset_code, e.name, e.category, e.status, e.version, e.created_at,
         l.id AS loan_id, l.due_date, u.display_name AS borrower_name,
         CASE WHEN e.status = 'DISPOSED' THEN 'DISPOSED'
              WHEN l.id IS NULL          THEN 'AVAILABLE'
              WHEN l.due_date &lt; #{today} THEN 'OVERDUE'
              ELSE 'LENT' END AS availability
    FROM equipment e
    LEFT JOIN loans l ON l.equipment_id = e.id AND l.returned_at IS NULL
    LEFT JOIN users u ON u.id = l.borrower_id
</sql>

<sql id="searchWhere">
  <where>
    <if test="keywordPattern != null">
      AND (t.name ILIKE #{keywordPattern} ESCAPE '\' OR t.asset_code ILIKE #{keywordPattern} ESCAPE '\')
    </if>
    <if test="categories != null and !categories.isEmpty()">
      AND t.category IN
      <foreach collection="categories" item="c" open="(" separator="," close=")">#{c}</foreach>
    </if>
    <choose>
      <when test="availability != null">AND t.availability = #{availability}</when>
      <otherwise>AND t.availability &lt;&gt; 'DISPOSED'</otherwise>
    </choose>
  </where>
</sql>

<select id="search" resultMap="equipmentSummary">
  SELECT * FROM (<include refid="equipmentWithAvailability"/>) t
  <include refid="searchWhere"/>
  ORDER BY
  <choose>
    <when test="sort.key.name() == 'NAME'">t.name</when>
    <when test="sort.key.name() == 'CATEGORY'">t.category</when>
    <when test="sort.key.name() == 'CREATED_AT'">t.created_at</when>
    <when test="sort.key.name() == 'DUE_DATE'">t.due_date</when>
    <otherwise>t.asset_code</otherwise>
  </choose>
  <if test="sort.descending">DESC</if> NULLS LAST, t.id
  LIMIT #{page.size} OFFSET #{page.offset}
</select>
```

| 一覧 | 絞り込み | 並び替えキー（既定） |
|---|---|---|
| 備品検索 | キーワード・区分（複数）・貸出状態 | `assetCode`（既定・昇順）・`name`・`category`・`createdAt`・`dueDate` |
| 貸出一覧 | `state`・`borrowerId`・`equipmentId` | `lentAt`（既定・降順）・`dueDate` |
| 延滞一覧 | なし（未返却かつ期限 < 今日） | 延滞日数の多い順で固定。`ORDER BY l.due_date, l.id` と列で書く（期限が古いほど延滞日数が多いので意味は同じ。式 `#{today} - l.due_date` で並べると索引の順に読めない） |

- 更新（PATCH）は `<set>` と `<if>` で送られた列だけを書く。
- 結果は Java の record に `resultMap` の `<constructor>` で対応付ける（暗黙の自動対応に頼らない）。

索引が効く所・効かない所:

- 延滞一覧は、部分索引 `ix_loans_open_due_date (due_date, id) WHERE returned_at IS NULL` の順に読める。
- 備品検索は索引がほぼ効かない。`'%kw%'` の `ILIKE` は B-tree 索引を使えず、availability は `CASE` 式で求めるので、その絞り込みも全件を貸出・利用者と結合してから判定する。`COUNT(*)` も同じ結合をする。
- 想定の規模（備品が数百〜数千件）では順次走査で足りると見ている（未測定）。増えたら、キーワードは `pg_trgm` の GIN 索引、ページングはキーセット方式に切り替える。
- 実装の後に、件数を明記した架空データで検索と延滞一覧の `EXPLAIN (ANALYZE, BUFFERS)` を取り、コマンドと日付つきで README に載せる（実測値だけを書く）。

- 依存の向きは `loan` → `equipment`・`user` の一方向。廃棄の時に「未返却があるか」を見るのは `EquipmentMapper` の SQL（`loans` を参照）で行い、Java のパッケージ依存を逆向きにしない。
- 業務日付・上限値は `LendingProperties`（`@ConfigurationProperties` の record）と `Clock` の Bean から受け取る。テストでは固定の `Clock` を渡す。
- 初期データ `R__demo_data.sql` は Flyway の繰り返し実行のマイグレーション（中身が変わるたびに再実行される）なので、何度流しても同じ結果になるように書く。備品は `INSERT … ON CONFLICT (asset_code) DO NOTHING`、利用者は `ON CONFLICT (email) DO NOTHING`。id は `GENERATED ALWAYS` で固定できないので、貸出は `(SELECT id FROM users WHERE email = '…')` のように自然キーで参照し、未返却の行だけを `ON CONFLICT (equipment_id) WHERE returned_at IS NULL DO NOTHING` で入れる。`application-demo.properties` で `spring.flyway.locations=classpath:db/migration,classpath:db/demo` にする。手元の DB は demo の有無で使い分けない（適用済みの R__ が見つからない状態を作らない）。

## 12. 認証（デモ方式）と非機能

- 利用者は `X-User-Id` ヘッダで受ける。`/api/**` に掛けた `HandlerInterceptor`（`AuthenticationInterceptor`）が `preHandle` でヘッダを検証し、`users` から引いた `CurrentUser(id, role)` を request 属性に置く。無い・数字でない・存在しない時は `UNAUTHENTICATED` の例外を投げる（`@RestControllerAdvice` に届く）。`CurrentUserArgumentResolver` は属性を読むだけ。
- **認証はハンドラより前に、全リクエストで判定する。** 引数（`@Valid @RequestBody` など）の解決より前なので、401 は 400 より先に返る。`CurrentUser` を引数に取らない API（検索・詳細）でも認証は効く。405・406・415 はハンドラを選ぶ段階で決まるので、401 より先になる。
- **誰でも他人の ID を名乗れるので、本番では使えない。** 本番では Spring Security のフィルタチェーン（OAuth 2.0 リソースサーバー。OIDC のプロバイダが発行したアクセストークンの `sub` を利用者に対応付ける）に置き換える。差し替えるのは interceptor とリゾルバだけで、サービスは `CurrentUser` しか知らないので変わらない。フィルタはハンドラを選ぶより前に動くので、本番では 401 がすべてに先立つ。
- 401 に `WWW-Authenticate` ヘッダを付けない。RFC 9110 §15.5.2 は 401 にチャレンジを必須としているが、デモ方式に対応する認証スキームが無いため（本番の OIDC では `WWW-Authenticate: Bearer` を返す）。
- `/v3/api-docs`・`/swagger-ui.html`・`/actuator/health` は `/api/**` の外なので認証しない。
- OpenAPI: springdoc で `/v3/api-docs` と `/swagger-ui.html` を出す。`CurrentUser` の引数は `@Parameter(hidden = true)` で隠し、`OperationCustomizer` で全操作にヘッダの引数 `X-User-Id`（必須）を足す（テスト計画 §3 の `OpenApiContractTest` の前提）。
- ログ: 個人情報（メールアドレス・表示名）をログに出さない。想定外の例外はスタックトレースを `traceId` と一緒にログにだけ出す。
- 設定・秘密: DB の接続情報は環境変数か `compose.yaml`（手元専用の値）で渡し、リポジトリに本物の秘密は置かない。
- Actuator は `health` だけを公開する。
- 性能の目標値は置かない（測っていないため）。一覧は `size` の上限 100 で 1 回の応答量を抑える。索引の効き方は §10。

失敗の列挙と振る舞い:

| 失敗 | 振る舞い |
|---|---|
| DB に接続できない・SQL の想定外の失敗 | 500 `INTERNAL_ERROR` と `traceId`。トランザクションはロールバック。詳細はログだけ |
| 権限がない・本人でない | 403。書き込みは 1 件も行わない |
| 一覧が空・範囲外のページ（`page` ≤ 10000） | 200 で `items` が空。`totalElements` は正しい件数 |
| `page` が 10000 を超える | 400 `VALIDATION_FAILED`（OFFSET の桁あふれを入口で止める） |
| 二重実行・同時実行 | §8 のとおり、成功 1 件と業務エラー（409・422）に分かれる。500 にはしない |
| 途中で落ちる | 1 操作 1 トランザクションなので、途中までの書き込みは残らない |
| 日付の境目・タイムゾーン | 業務日付は `lending.zone` で求め、1 操作の中では同じ日付を使う（§5）。サーバーや JVM のタイムゾーンに依存しない |

## 13. 採らなかった案と理由

| 採らなかった案 | 理由 |
|---|---|
| **JPA（Spring Data JPA）** | この API の要点は SQL そのもの（部分一意インデックスに当たる INSERT、`FOR UPDATE`、`CASE` で求める状態、条件の組み合わせ検索、延滞日数の計算）。MyBatis なら発行される SQL がそのまま XML で読め、レビューの対象にできる。JPA では変更の自動検出による暗黙の UPDATE、関連の遅延読み込みによる N+1 を別に意識する必要があり、`FOR UPDATE` や部分一意インデックスは結局 SQL 方言や native query に寄る |
| Spring の `JdbcClient` だけで書く | 依存は減るが、条件で変わる SQL を Java の文字列連結で組むことになり、読みやすさと注入対策の確認がしにくい |
| MyBatis の注釈で SQL を書く | 動的 SQL が長くなると読めない。XML に統一する |
| 二重貸出を楽観ロックだけで防ぐ | §8。貸出は行の追加で、`version` 列では守れない。守るには貸出のたびに備品行を更新することになり、備品情報の編集が無関係に 409 になる |
| 備品に `LENT` を保存する | 「貸出中」の情報が `loans` と二重になり、片方だけ更新されるとずれる。導出すれば正本は 1 つ |
| SERIALIZABLE 分離レベル＋再試行 | 正しく守れる（件数のファントムも述語ロックで検出する）が、競合は直列化エラーとして後から届くので再試行が要り、業務エラー（409・422）への対応付けが分かりにくい。悲観ロックなら「何で直列化しているか」が SQL に見える |
| 業務ルールを DB のトリガで書く | ルールが Java から見えず、Mockito の単体テストで確かめられない |
| 延滞フラグを夜間バッチで立てる | 日付が変わってからバッチまでの間、表示がずれる。バッチの運用も要る。「期限 < 今日」で毎回求めれば足りる |
| キーセット方式のページング | 想定データ量（数百〜数千件）では OFFSET で足り、ページ番号で飛べる方が画面に合う。増えた時の切り替えは §10 |
| 認証を引数リゾルバだけで行う（v0.1 の案） | `CurrentUser` を引数に取らない API で認証が働かず、`@Valid @RequestBody` が先に解決されると 401 より先に 400 が返る |
| 借り手と返却期限を ADMIN と本人だけに見せる | 応答から落とすだけでは足りず、`availability=OVERDUE` の絞り込みと `dueDate` の並び替えからも分かる。検索条件まで役割で変えることになり、社内の台帳としての使い道（今の持ち主に頼む）も失う。要件になったら、応答の組み立てと検索条件の両方を役割で分ける |
| 他人の貸出を 404 にして存在を隠す | 貸出の ID の存在は社内で隠す情報ではない。403 の方が利用者が原因（権限）を取り違えない |
| PATCH を JSON Merge Patch（RFC 7396）にする | `null`＝削除の約束だと、必須の項目（名称・区分）に `null` が来た時の 400 を別に決める必要がある。送った項目だけを変える独自の形の方が短く書ける |
| `If-Match` / `ETag` で `version` を受ける | HTTP としてはより正統だが、サンプルとしては本文の `version` の方が読みやすい。差し替えは容易 |
| `type` は `about:blank` のまま `code` だけで区別する（v0.1 の案） | RFC 9457 では `about:blank` は「HTTP の状態以上の意味を持たない問題」を表す。`code` で意味を分けるなら `type` でも分けるのが仕様の意図。`type` は解決できない URI でもよく、説明ページの置き場は前提にならない |
| 401 に独自のチャレンジ（`WWW-Authenticate: X-User-Id`）を付ける | どのクライアントも解釈しない値で形だけ合わせることになる。デモの認証は差し替える前提 |
| 認証を今作る（Spring Security） | サンプルの主題から外れ、読む量が増える。差し替え点を interceptor とリゾルバに閉じ込めて範囲外にした |
| ArchUnit などで層の依存を検査 | 規模が小さく、パッケージ 3 つの依存は目で追える。依存を増やさない |
