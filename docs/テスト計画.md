## 1. 方針

- テストは回帰を検知するために書く。業務ルール 1 つにつき、正常系（守れている場合）と異常系（破った場合）の両方を置く。
- 速いテストを多く、DB を使うテストは SQL と制約とロックを確かめる所に絞る。

| 層 | 道具 | 何を確かめるか | DB |
|---|---|---|---|
| 単体 | JUnit・AssertJ・Mockito | サービスの業務ルール・判定の順番・権限・例外の変換・時刻の境目。並び替えの解釈・キーワードのエスケープ | 使わない |
| マッパー（DB） | `@MybatisTest`＋Testcontainers（`postgres:17`） | 動的 SQL の条件の組み合わせ・並び順・ページング・状態の導出・制約・条件付き UPDATE | 本物の PostgreSQL |
| API（Web 層） | `@WebMvcTest`＋`MockMvcTester`（サービスは `@MockitoBean`） | HTTP の状態・`Location`・認証の順番・入力検証・ProblemDetail の形・ヘッダ | 使わない |
| E2E | `@SpringBootTest(webEnvironment = RANDOM_PORT)`＋`RestTestClient`＋Testcontainers | 登録から廃棄までを HTTP で 1 本通す・OpenAPI と API 一覧の一致 | 本物の PostgreSQL |
| 同時実行 | `@SpringBootTest`＋Testcontainers＋スレッド | 二重貸出・件数上限・廃棄との競合・返却の二重実行を実際に並列で起こす | 本物の PostgreSQL |

- 本物の DB を使うテストは、H2 などの代わりの DB を使わない（部分一意インデックス・`FOR UPDATE`・`ILIKE` の振る舞いは PostgreSQL のものを確かめたい）。
- コンテナ: `TestcontainersConfiguration`（`@Bean @ServiceConnection` の `PostgreSQLContainer`）は、アプリケーション文脈と一緒に起動・停止する。Spring のテスト文脈キャッシュにより、同じ設定のテストクラスは文脈とコンテナを共有する。設定を次の 2 種類だけにするので、**コンテナは 2 つ**（マッパー用と、アプリ全体用）。
- 付け忘れと設定のばらつきを防ぐため、DB を使うテストは 2 つの合成注釈のどちらかを付ける。

| 合成注釈 | 中身 | 使うテスト |
|---|---|---|
| `@MapperDbTest` | `@MybatisTest`・`@AutoConfigureTestDatabase(replace = NONE)`・`@Tag("docker")`・`@Import({TestcontainersConfiguration.class, TestData.class})` | マッパー（DB） |
| `@AppDbTest` | `@SpringBootTest(webEnvironment = RANDOM_PORT)`・`@AutoConfigureRestTestClient`（Boot 4 では `@SpringBootTest` だけでは `RestTestClient` が注入されない）・`@Tag("docker")`・`@Import({TestcontainersConfiguration.class, MutableClockConfiguration.class, TestData.class})` | E2E・同時実行・`OpenApiContractTest`・start.spring.io が生成する `contextLoads` |

- `@AppDbTest` のクラスに `@MockitoBean` などクラスごとの差分を足さない（文脈が分かれ、3 つ目のコンテナが立つ）。
- 後片付け（実行順で結果が変わらないように）:
  - マッパー（DB）のテストは各テストがロールバックされる。それでも空の DB を前提にせず、件数や並び順を確かめるテストは、自分のトランザクションの中で先に 3 表を空にしてから行を入れる（ロールバックで元に戻る）。
  - COMMIT するテスト（E2E・同時実行）は、`@BeforeEach` で `TestData.reset()` を呼ぶ。中身は `TRUNCATE loans, equipment, users RESTART IDENTITY CASCADE` と、`MutableClock` を基準の時刻（2026-10-05 10:00 日本時間）に戻すこと。前のテストが残した行（`PC-0001`・山田さんたち）や進めた時計に結果を左右させない。
- 時刻: 単体は固定の `Clock` を渡す。`@AppDbTest` の文脈は、時計を進められる `MutableClock`（テスト用の小さな `Clock` の実装）を使う。`MutableClockConfiguration` はこれを本体の `ClockConfig` と別の Bean 名で `@Primary` を付けて登録する（同じ名前だと Bean の上書き禁止で起動に失敗し、`@Primary` が無いと `Clock` が 2 つで注入に失敗する）。

### 4-4. E2E（`@AppDbTest`＋`RestTestClient`）

`LendingApiEndToEndTest` で 1 本のシナリオを順に流す（`@BeforeEach` で `TestData.reset()`。時計は 2026-10-05 10:00 日本時間から）。

1. ADMIN が `PC-0001` を登録 → 201・`Location` を GET すると同じ内容
2. MEMBER（山田）が `availability=AVAILABLE` で検索 → 含まれる

4. MEMBER（佐藤）が検索 → `PC-0001` に借り手「山田 太郎」と返却期限が出る。応答に `email` は無い

## 5. 同時実行テスト

`ConcurrentLendingTest`（`@AppDbTest`）。**テストのメソッドには `@Transactional` を付けない**（各スレッドが別々のトランザクションで COMMIT しないと競合が起きないため）。`@BeforeEach` で `TestData.reset()`（§1）を呼んでから、そのテストの備品と利用者を作る。

並べ方（全テスト共通）:

1. スレッド数 N の `ExecutorService` を作る（N は接続プールの上限 10 より小さい 8 にし、接続待ちで競合が薄まらないようにする）。
2. 各スレッドは `CountDownLatch ready` を数えてから `CountDownLatch start` で待つ。全員がそろってから `start.countDown()` で一斉に呼ぶ。
3. 結果は `Future` で集め、1 本 30 秒で打ち切る（固まった時にテストが終わらないのを防ぐ）。
4. 呼び出しはサービスの公開メソッド（HTTP を挟まない。競合の窓を広げるため）。

| ID | 起こす競合 | 判定（すべて満たして緑） | 対応 |
|---|---|---|---|
| CT-1 | 空いている備品 1 台を、別々の利用者 8 人が同時に借りる | 成功 1／`EQUIPMENT_ALREADY_LENT` 7／それ以外の例外 0／DB の未返却はその備品で 1 件 | AC-16・R1 |
| CT-2 | アプリの判定を通らずに、2 本のトランザクションで同じ備品の未返却を同時に INSERT | 1 本が成功、もう 1 本が `DuplicateKeyException`（制約だけで止まることの確認） | R1 |
| CT-3 | 未返却 0 件の利用者 1 人が、別々の備品 6 台を同時に借りる | 成功ちょうど 3／`LOAN_LIMIT_EXCEEDED` 3／DB の未返却 3 件 | AC-17・R6 |
| CT-4 | 空いている備品 1 台に、廃棄 1 本と貸出 1 本を同時に | 結果は「貸出成功＋廃棄 409 `EQUIPMENT_IN_USE`」か「廃棄成功＋貸出 409 `EQUIPMENT_DISPOSED`」のどちらか。DB に「廃棄済みで未返却あり」が 0 件 | AC-18・R2・R3 |
| CT-5 | 同じ貸出を 2 本同時に返却 | 成功 1／`LOAN_ALREADY_RETURNED` 1 | R7 |

- 競合は毎回同じ順で起きるとは限らないので、CT-1・CT-3・CT-4 は `@RepeatedTest` で繰り返す（回数は実装の後に所要時間を測って決め、ここに書く）。
- **手動のミューテーション確認**（排他制御を 1 か所ずつ外し、テストが赤になることを確かめる。実装の後に 1 回だけ手で行い、結果を残して元に戻す）:

| 外す物 | 赤になるはずのテスト | 結果（実測を記入） |
|---|---|---|
| M1: 利用者行の `FOR UPDATE` | CT-3 | 未測定 |
| M2: 備品行の `FOR UPDATE` | CT-4（CT-1 は制約と例外の変換で緑のまま＝二重の守りが効いている） | 未測定 |
| M3: 部分一意インデックス | CT-2・`SchemaConstraintTest` | 未測定 |
| M4: M2 に加えて `DuplicateKeyException` の変換 | CT-1（想定外の例外が混ざる） | 未測定 |

競合に頼るテストは 1 回では赤にならないことがあるので、「何回の繰り返し中、何回赤になったか」を書く。
