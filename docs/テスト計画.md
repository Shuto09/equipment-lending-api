# テスト計画 — 社内備品の貸出管理 API

- 版: v0.1（2026-10-04）／状態: 実装前の計画
- この文書は Claude Code（Anthropic の AI）で作成しました。
- 対象の仕様: [要件と設計.md](要件と設計.md)（受け入れ条件 AC-01〜AC-20・業務ルール R1〜R9）

## 1. 方針

- テストは「動いた証拠」ではなく「壊れたら分かる装置」として書く。業務ルール 1 つにつき、守れている場合と破った場合の両方を置く。
- 速いテストを多く、DB を使うテストは SQL と制約とロックを確かめる所に絞る。

| 層 | 道具 | 何を確かめるか | DB |
|---|---|---|---|
| 単体 | JUnit・AssertJ・Mockito | サービスの業務ルール・判定の順番・権限・例外の変換・時刻の境目。並び替えの解釈・キーワードの逃がし | 使わない |
| マッパー | `@MybatisTest`＋Testcontainers（`postgres:17`） | 動的 SQL の条件の組み合わせ・並び順・ページング・状態の導出・制約・条件付き UPDATE | 本物の PostgreSQL |
| API | `@WebMvcTest`＋`MockMvcTester`（サービスは `@MockitoBean`） | HTTP の状態・`Location`・入力検証・ProblemDetail の形・ヘッダ | 使わない |
| 通し | `@SpringBootTest(webEnvironment = RANDOM_PORT)`＋`RestTestClient`＋Testcontainers | 登録から廃棄までを HTTP で 1 本通す・OpenAPI と API 一覧の一致 | 本物の PostgreSQL |
| 同時実行 | `@SpringBootTest`＋Testcontainers＋スレッド | 二重貸出・件数上限・廃棄との競合・返却の二重実行を実際に並列で起こす | 本物の PostgreSQL |

- 本物の DB を使うテストは、H2 などの代わりの DB を使わない（部分一意インデックス・`FOR UPDATE`・`ILIKE` の振る舞いは PostgreSQL のものを確かめたい）。
- Testcontainers のコンテナは `TestcontainersConfiguration`（`@ServiceConnection`）1 つを全クラスで共有し、Spring のテスト文脈のキャッシュで使い回す。
- 時刻は固定の `Clock` を渡す。通しテストだけは時計を進められる `MutableClock`（テスト用の小さな `Clock` の実装）を使う。

## 2. 実行のしかた

| 目的 | コマンド | Docker |
|---|---|---|
| 単体と API の層だけ（速い） | `./mvnw -B -ntp test -DexcludedGroups=docker` | 不要 |
| 全部 | `./mvnw -B -ntp verify` | 要る |
| CI | GitHub Actions（`ubuntu-latest`・Temurin 21）で `./mvnw -B -ntp verify` | ランナーに入っている |

- DB を使うテストクラスには `@Tag("docker")` を付ける（上の `-DexcludedGroups=docker` で外せるように）。
- 所要時間・本数は実装後に実測して README に書く（コマンドと日付つき）。

## 3. 機械的な検査（文書と実装のずれを止める）

| 検査 | テスト | 失敗の条件 |
|---|---|---|
| マッパー XML に `${` が無い（SQL 注入の経路を作らない） | `MapperXmlSafetyTest` | `src/main/resources/mapper/**/*.xml` に 1 つでもある |
| マッパー XML に `now()`・`CURRENT_DATE`・`CURRENT_TIMESTAMP` が無い（時刻はアプリの `Clock` から） | 同上 | 同上（大文字小文字を区別しない） |
| 上の検査が効いていること（陽性対照） | 同上 | `${x}` や `now()` を含む見本の文字列を検査関数に渡して「見つかった」にならない |
| API 一覧（設計 §6 の 10 本）と OpenAPI の出力が一致 | `OpenApiContractTest` | `/v3/api-docs` の「メソッド＋パス」の集合が 10 本の表と一致しない／`X-User-Id` が載っていない操作がある |
| `ErrorCode` のすべてが HTTP 状態と `code` に変換される | `ApiExceptionHandlerTest`（`ErrorCode.values()` で繰り返す） | 変換の漏れ・状態の取り違え |

| テストクラス | 主なテスト |
|---|---|
| `EquipmentMapperTest` | キーワード: 名前・管理番号の部分一致・大文字小文字を区別しない・`%` と `_` は文字として（「100%充電器」は当たり「1000 円」は当たらない）・`' OR '1'='1` は 0 件で表は無事／区分: 1 つ・複数・空のリストは絞らない／貸出状態: 4 つの値と既定（廃棄済みを除く）・期限が今日なら `LENT`、昨日なら `OVERDUE`／並び替え: 全キーの昇順・降順、同じ値の行は `id` 順、`dueDate` の空は最後／ページ: 0 ページ目と最後のページ、範囲外のページは空で件数は変わらない、件数の文と一覧の文の条件が一致／版つき UPDATE: 版が合えば 1 件で版が 1 増える、古い版と廃棄済みは 0 件／未返却の有無／`OffsetDateTime` の往復で時刻が変わらない |

### 4-4. 通し（`@SpringBootTest`＋`RestTestClient`）

`LendingApiEndToEndTest` で 1 本のシナリオを順に流す（時計は 2026-10-05 10:00 日本時間から始める）。

1. ADMIN が `PC-0001` を登録 → 201・`Location` を GET すると同じ内容
2. MEMBER（山田）が `availability=AVAILABLE` で検索 → 含まれる
3. 山田が期限 2026-10-12 で借りる → 201
4. MEMBER（佐藤）が同じ備品を借りる → 409・ProblemDetail の `code` が `EQUIPMENT_ALREADY_LENT`
5. 時計を 2026-10-14 に進める → ADMIN の延滞一覧に 1 件・延滞日数 2
6. 山田が返却 → 200・`returnedLate=true`
7. ADMIN が廃棄 → 200。佐藤が借りる → 409 `EQUIPMENT_DISPOSED`。既定の検索結果から消える
8. `X-User-Id` なしで検索 → 401

`OpenApiContractTest` も同じ設定で動かす（§3）。

## 5. 同時実行テスト

`ConcurrentLendingTest`（`@SpringBootTest`・`@Tag("docker")`）。**テストのメソッドには `@Transactional` を付けない**（各スレッドが別々のトランザクションで確定させないと競合が起きないため）。毎回、新しい備品と利用者を作ってから始め、`@AfterEach` で表を空にする。

並べ方（全テスト共通）:

1. スレッド数 N の `ExecutorService` を作る（N は接続プールの上限 10 より小さい 8 にし、接続待ちで競合が薄まらないようにする）。
2. 各スレッドは `CountDownLatch ready` を数えてから `CountDownLatch start` で待つ。全員がそろってから `start.countDown()` で一斉に呼ぶ。
3. 結果は `Future` で集め、1 本 30 秒で打ち切る（固まった時にテストが終わらないのを防ぐ）。
4. 呼び出しはサービスの公開メソッド（HTTP を挟まない。競合の窓を広げるため）。

| ID | 起こす競合 | 判定（すべて満たして緑） | 対応 |
|---|---|---|---|
| CT-1 | 空いている備品 1 台を、別々の利用者 8 人が同時に借りる | 成功 1／`EQUIPMENT_ALREADY_LENT` 7／それ以外の例外 0／DB の未返却はその備品で 1 件 | AC-16・R1 |
| CT-2 | アプリの判定を通らずに、2 本のトランザクションで同じ備品の未返却を同時に INSERT | 1 本が成功、もう 1 本が `DuplicateKeyException`（制約だけで止まることの確認） | R1 |
| CT-3 | 未返却 0 件の利用者 1 人が、別々の備品 6 台を同時に借りる | 成功ちょうど 3／`LOAN_LIMIT_EXCEEDED` 3／DB の未返却 3 件 | AC-17・R6 |
| CT-4 | 空いている備品 1 台に、廃棄 1 本と貸出 1 本を同時に | 結果は「貸出成功＋廃棄 409 `EQUIPMENT_IN_USE`」か「廃棄成功＋貸出 409 `EQUIPMENT_DISPOSED`」のどちらか。DB に「廃棄済みで未返却あり」が 0 件 | AC-18・R2・R3 |
| CT-5 | 同じ貸出を 2 本同時に返却 | 成功 1／`LOAN_ALREADY_RETURNED` 1 | R7 |

- 競合は毎回同じ順で起きるとは限らないので、CT-1・CT-3・CT-4 は `@RepeatedTest` で繰り返す（回数は実装後に所要時間を測って決め、ここに書く）。
- **壊れたら分かることの確認**（実装後に 1 回だけ手で行い、結果を残して元に戻す）:

| 手で入れる壊し方 | 赤になるはずのテスト | 結果（実測を記入） |
|---|---|---|
| M1: 利用者行の `FOR UPDATE` を外す | CT-3 | 未測定 |
| M2: 備品行の `FOR UPDATE` を外す | CT-4（CT-1 は制約と例外の変換で緑のまま＝二重の守りが効いている） | 未測定 |
| M3: 部分一意インデックスを作らない | CT-2・`SchemaConstraintTest` | 未測定 |
| M4: M2 に加えて `DuplicateKeyException` の変換を外す | CT-1（想定外の例外が混ざる） | 未測定 |

競合に頼るテストは 1 回では赤にならないことがあるので、「何回の繰り返し中、何回赤になったか」を書く。
